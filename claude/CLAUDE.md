# 개인 규칙

모든 프로젝트에 공통 적용되는 전역 지침.

## 개발 워크플로

**조사 → 개발 → 테스트 → 리뷰 → 커밋** 순서를 지킨다.

1. **조사** — 개발 전에 관련 컨텍스트(기존 코드, 문서, 컨벤션)를 먼저 파악하고 확장한다.
2. **개발** — 파악한 컨벤션에 맞춰 구현한다.
3. **테스트** — 테스트 코드를 항상 작성하고 통과를 확인한다.
4. **리뷰** — 서브에이전트와 페르소나 부여 리뷰어를 통해 검토한다.
5. **커밋** — 수정 → 테스트 → 리뷰를 반복해 문제가 없을 때만 커밋한다.

## 작업 원칙

- 검증하지 않은 완료 선언을 하지 않는다 — "됐다"고 말하려면 실행한 명령과 그 출력을 근거로 보여준다.
- 요청받지 않은 리팩터·리네임·포맷·정리를 하지 않는다. 필요해 보이면 하지 말고 말한다.
- 요청받은 범위만큼만 만든다 — 나중에 필요할 것 같은 추상화·설정·옵션을 미리 넣지 않는다.
- 고치기 전에 읽는다 — 대상 파일과 그 함수의 호출부를 먼저 확인한다.
- 불확실하면 추측하지 않는다. 모르는 채로 진행하는 것보다 묻는 게 싸다.
- 코드베이스에 상반된 패턴이 둘 있으면 섞지 않는다.
  - 어느 쪽이 맞는지 명확한 근거(더 최신·더 널리 쓰임·테스트 있음)가 있으면 골라서 이유를 밝히고 진행한다.
  - 근거가 애매하거나 정보가 부족하면 진행하지 말고 나와 정한다.

## 실행 원칙

- 브라우저로 확인할 때는 **항상** headless(백그라운드)로 실행한다 (Playwright 등). 창을 띄우지 않는다.
- 그 외에도 작업을 가로채는 명령을 쓰지 않는다 — 사람 입력을 기다리거나 화면을 점유하면 세션이 멈춘다.
  - pager를 띄우지 않는다 (`git --no-pager log`).
  - 인터랙티브 모드 대신 플래그로 답을 준다 (`npm init -y`, `gh pr create --fill`).

## 실패 처리

- 폴백·무음 복구·기본값 채우기로 에러를 가리지 않는다 — 원인이 묻히면 디버깅 비용이 몇 배가 된다.
- 실패는 명시적으로 올리고, 메시지에 무엇이 왜 실패했는지 담는다.
- 요청받지 않은 방어 코드(`try/except: pass`, 광범위한 catch)를 추가하지 않는다.

## Git 커밋

### 메시지

- 영어로 작성하고 Conventional Commits(`feat:`, `fix:`, ...)를 준수한다.
- 제목은 깔끔한 한 줄. 본문은 필요할 때만, 영어 개조식으로 간결하게.

### 히스토리

- 아직 푸시되지 않은 커밋을 수정할 때는 새 커밋을 쌓지 않고 해당 커밋에 amend/fixup으로 합친다.

## 프로젝트 규칙 파일

- 프로젝트 규칙은 루트 `AGENTS.md`에 쓴다 — 특정 에이전트에 종속되지 않는다.
- `CLAUDE.md`에는 규칙을 쓰지 않고 `@AGENTS.md` 한 줄로 링크만 한다.

## AI 작업 문서

- 요청받지 않은 문서(README, 요약, 마이그레이션 가이드)를 만들지 않는다 — 코드가 1차 문서다.
- AI와 함께 정리하는 문서는 프로젝트 루트의 `.docs/`에 둔다.
- `.docs/.gitignore`를 만들고 내용은 `*` 한 줄만 — 폴더 전체를 git 추적에서 제외한다.

## Python

- 환경·의존성·실행은 항상 `uv`를 사용한다 (`uv add`, `uv run`, ...).
- 린트/포맷은 `ruff`.

### 테스트 (`pytest`)

- 테스트는 `pytest`로 작성하고 `uv run pytest`로 실행한다.
- `tests/` 폴더는 소스 코드와 1:1로 같은 폴더 구조를 유지한다 (예: `src/pkg/mod.py` → `tests/pkg/test_mod.py`).
- 테스트 파일은 `test_*.py`, 테스트 함수는 `test_*`로 명명한다.
